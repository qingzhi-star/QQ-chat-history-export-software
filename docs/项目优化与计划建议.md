# 项目优化与计划建议

**审阅日期：** 2026-10-27  
**用途：** 供后续实现、验收和文档维护参考；本文件是建议稿，不替代规范性决策。

## 一、审阅范围与当前判断

本建议依据项目交接文档、P0 设计规格、完整的 13 项实现计划、修正案 A、Task 1–5 的任务报告，以及已完成的源码和测试。规则冲突时按交接约定执行：**修正案 A > 设计规格 > 原实现计划**。本次只读审阅，没有运行项目代码或测试。

交接记录 Task 1–5 已完成，P0 后续仍有 Task 6–13；密钥扫描、密钥存储、解密编排、doctor 和 CLI 尚未全部打通。因此现阶段应继续把目标定为“完成并证明 P0”，不要提前把 README 或对外说明改成 P0 已完成。交接中记录的测试结果是历史结果，本次没有复跑。

项目已有几项值得保留的工程基础：SQLCipher 有独立 known-answer tests；WAL 与快照以合成数据覆盖竞态和失败路径；Task 4–5 报告包含真实变异测试结果；源数据只读、脱敏和失败降级被列为硬约束。后续应继续把“实现正确”“真实 QQ 格式兼容”“实际运行时安全”作为不同证据，不以合成测试或单次成功解密替代真机验收。

## 二、优先处理的项目级问题

### P0：清理已有文档中的本机路径

设计规格的测试矩阵中仍留有一个具体 Windows 用户目录示例（见设计规格约第 1034 行，计划书约第 586 行引用了同一背景）。建议在独立文档修订中改成 `<user>`、`%USERPROFILE%` 或纯合成路径，并检查其历史复制位置。不要把真实路径复制进新计划、报告、测试输出或提交说明。

当前隐私扫描主要用于检查将要提交的改动；建议另加一个只读的全库文档审计入口，扫描全部受版本控制的 Markdown、示例配置和脚本片段。两类检查各自保留：提交差异检查拦截新泄露，全库巡检清理历史遗留。对合成测试口令和明确允许的样例继续使用窄范围 allowlist，并让扫描输出只报告文件、行号和类别。

### P0：让后续任务只从当前有效规范生成

原计划包含已被修正案替代的代码片段和验收口径。继续直接照旧片段执行，可能重新引入已裁定要移除的口令位置参数、非 TTY 下不安全的 getpass 回退、默认选择第一个账号、把 SKIP 当作通过、或不完整的 WAL / 明文清理验证。

建议在启动 Task 6 前先建立一份新的执行 brief：只摘录该任务适用的交接约束、修正案 A 对应条款、当前接口和退出条件；旧计划保留作历史记录，并在过时的代码块附近加“已由修正案 A 替代”的醒目标注。Task 6 的 brief 尚未出现在已留存的任务 brief 文件中，宜在执行前补齐，避免把主计划中的旧实现段落当成最终规格。

每个任务完成时记录四项：代码与测试变化、通过/未验证项、隐私扫描结果、与计划不同的实现决定。把 PASS、WARN、FAIL、SKIP、UNVERIFIED 分开记录；未运行、未取得真实证据或被跳过的项目不可计为 PASS。

## 三、P0 建议执行顺序与各任务出口

按修正案 A 的顺序继续；每一项都应在进入下一项前完成自身的接口、失败路径和隐私复核。

| 阶段 | 任务 | 关键执行建议 | 出口条件 |
|---|---|---|---|
| 系统边界 | Task 6：keyscan | 内存读取保持显式 opt-in；仅申请查询和读取权限；以目标数据库 page-1 HMAC 验证候选密钥。用假 reader 覆盖进程退出、部分读取、权限拒绝、扫描超时和竞态，并在测试中核对实际 OpenProcess 权限与调用次数。 | 默认 doctor 不扫描进程；没有任何更高权限重试、注入或写内存路径；多进程只接受与所选账号数据库匹配的候选。 |
| 系统边界 | Task 7：keystore | 损坏或未知版本的存储应明确报告损坏，不能悄悄当作空存储；隔离坏条目；使用唯一临时文件和原子替换；清楚记录 DPAPI 的保护边界。密钥不得通过环境变量或日志流转。 | 崩溃/写入失败后旧存储仍完整、临时文件可清理；输出和报告只含指纹或掩码，不含密钥本体。 |

### Task 2 的测试补强

交接已指出扫盘剪枝测试使用空噪声目录，删掉剪枝逻辑也可能继续通过。建议在后续测试维护中放入实际子目录和文件，并断言该分支确实没有继续遍历；同时隔离显式目录测试中的真实机器发现入口，避免单测因开发机状态改变结果或输出隐私数据。由于 Task 9 需展示扫描截断信息，应通过公开的 find_tencent_files 结果传递该信号，不改变已冻结的 discover_accounts 签名。

## 四、P0 之后的改进建议

1. **兼容性 CI：** pyproject 声明支持 Python 3.12 起，交接记录的本机验证环境是 Python 3.14。按修正案将 3.12 的验证放到 CI，至少运行 Windows 上 Python 3.12 和 3.14 的合成测试；live 与含真实数据的 fixture 不上传、不放进常规 CI。
2. **内存上界：** WAL 为保证只提交完整事务而缓冲 pending pages。补充最大事务体量/内存观测及超限降级策略，确保异常大的 WAL 事务不会造成不可控内存占用，也不会把未提交页写入产物。
3. **配置健壮性：** 给 Config.load 增加字段类型和版本校验；并发保存或中断写入时保留旧配置、清理唯一临时文件。此项不阻断当前 P0 主链路，可放在 P1 加固。
4. **后续产品计划：** P1 的解析与导出计划应以 Task 13 脱敏后的真实表/列事实为输入，明确未知版本的诊断、数据范围选择、输出文件位置和明文生命周期；不要从设计规格中的预期字段直接推导真实数据库结构。

## 五、验收与协作约定

- 保持源 QQ 数据只读；代码只能读源库、复制到临时位置并在那里恢复/解密。对一致性的表述按 best_effort / unverified / proven 的实际条件，不把“尝试拿锁”等同于“已证明”。
- 合成、known-answer、变异测试验证算法和边界；fixture 验证真实页格式；live 验证运行时 WAL、资源清理和只读性。报告中分别写出证据来源和限制。
- 每次实现按交接约定提交一个中文 feat/fix/test/docs commit；完成 diff、隐私和副作用复核后再推送。新增任务材料必须遵守脱敏规则，避免复用历史台账里的真实账号、路径或输出。
- 本轮没有运行测试，因此不能把交接中的历史测试数写成本轮验证结论。建议文档中的项目状态只随 Task 13 的验收表更新。
